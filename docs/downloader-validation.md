# Проверка загрузчика — 2026-11-17

Обновление надёжности развёрнуто из PR #17; последующее уточнение пользователя:
слайдшоу должно показывать фото по 3 секунды, независимо от длины музыки.
При наличии Live Photo новое правило: каждый кадр длится столько же, сколько
самый длинный живой кадр, минимум 2 секунды. Без живых кадров остаются 3 секунды.
Полная приёмка Downloader 1.0
не объявляется пройденной до проверки всех обязательных сетевых сценариев.

## Автоматические проверки

Полный локальный прогон: Python unit/integration tests, Ruff, FFmpeg/ffprobe,
yt-dlp CLI, Deno и Chromium. Включает существующие проверки изоляции владельцев
архива, очереди, неопределённой доставки, восстановления, кнопок и очистки.
Дополнительно проверяются тихий fallback на фото при сбое музыки/рендеринга,
смешанные альбомы, групповые режимы и кнопки, предел 72 часа без продления,
видеодорожка Live Photo при её наличии в метаданных, одно фото с длинным/коротким аудио.
Дополнительно: длина всех кадров по Live Photo, несколько живых кадров разной
длины, минимум 2 секунды, короткая музыка не обрезает единственный живой кадр,
лимит общей длительности до рендеринга и совместимая отправка движения как видео.

## Реальные источники

Локальная сеть, текущий lock-файл, без cookies источников:

| Сценарий | Наблюдение |
| --- | --- |
| Присланная пользователем TikTok Story, короткий URL | MP4 15,02 с, H.264/AAC, 576×1024. Проверены 15 кадров в разные секунды: 15 разных хешей, движение сохранено. |
| Присланный TikTok Photo Mode с Live Photo | После дополнительного поиска motion URL получены фото + клип 3,433333 с. Новая локальная проверка pipeline: слайдшоу 6,866667 с, все 17 кадров второй половины при 5 fps различаются. «Фото» выбирает фото + полный короткий MP4. |
| Повторный запрос Story до добавления прямого page fallback | Наблюдался временный `source_blocked`. Успешная проверка не означает постоянную доступность источника. |

На VPS в изолированном контейнере с новым кодом, без production-данных:

- Photo Mode из присланной ссылки и YouTube: скачаны MP4 со звуком.
- Story из присланной ссылки: первоначально `source_blocked`, повторная попытка
  успешна со звуком. Отказы временные, число повторов ограничено.
- Instagram Reel и Story из upstream-примеров: `source_temporary`; успешная
  загрузка и отправка не подтверждены. Story из примера может быть устаревшей.
- Vimeo из upstream-примера: `authentication`, доступный файл не получен.

macOS ARM runner не получал задания: GitHub сообщил о нехватке capacity и
`The job was not acquired by Runner of type hosted even after multiple attempts`.
Матрица сохраняет проверку macOS на поддерживаемом `macos-26-intel`.

Диагностика Live Photo проверяла `/photo/`, `/video/`, публичный item detail,
embed/player и доступные публичные app endpoints. JPEG не содержат встроенного MP4.
Последующий разбор нашёл видеочасть через TikWM: второму кадру соответствует
MP4 3,433333 с, H.264/AAC, 1026×576, 403230 байт с `tiktokcdn-us.com`.
Проверка исходного клипа: 17 из 17 кадров при 5 fps имеют разные хеши.
Первое исправление собрало слайдшоу 6,0 с с сохранённым движением.
Новое правило длительности проверено выше; пара неподвижного и живого оригинала
сохраняется в manifest, при отправке живой кадр представлен обычным видео.

В production нативная отправка через `InputMediaLivePhoto` сохранила motion-track:
проверка точного второго сообщения из альбома вернула `live_photo`, 3,433333 с,
17 разных кадров при 5 fps. Однако пользователь сообщил, что на iPhone и Windows
получает статичное отображение. Ответ Bot API не устанавливает совместимость
клиента. Поэтому доставка живого кадра переключена на обычный короткий MP4
в той же позиции альбома; старый native `file_id` не используется как video.

TikWM используется только для дополнительного поиска motion URL у постов,
подтверждённых открытыми состоянием TikTok. Передаётся числовой ID; не передаются
исходные приватные/подписанные ссылки, cookies или Telegram-данные. ID результата,
количество, порядок и идентификаторы всех неподвижных фото должны совпасть.
Принимаются только HTTPS-адреса CDN TikTok. Внешний сервис остаётся зависимостью
этого дополнительного поиска; при отказе фото сохраняются, неполный результат
не переиспользуется через Telegram file_id и перепроверяется при новом запросе.
`TIKTOK_LIVE_PHOTOS=false` отключает поиск. Чужие credentials и обход приватности
не используются.

## Что ещё требует живой приёмки

Фактическая отправка новой версии через Telegram, групповые режимы и кнопки,
Business с обеих сторон, Instagram Story и карусель, остальные заявленные платформы,
перезапуск production и истечение реальных 72 часов. Автотесты не подменяют эти пункты.

После первого деплоя Telegram подтвердил отправку MP4, оригинальных фото и аудио
в личке. Пользователь подтвердил получение старого неподвижного слайдшоу.
Изменения длительности и совместимой отправки требуют отдельной проверки
Telegram после CI/деплоя. Снимок Windows-медиапросмотрщика получить не удалось:
`window crop is outside captured monitor`, повтор после обновления выбора окна
дал ту же ошибку; дальнейшая автоматизация окна остановлена.

Деплой выполняется существующим workflow: feature branch → PR checks → merge
→ полный CI → неизменяемый образ → резервная копия базы → healthy и HTTPS checks.
