# Проверка загрузчика — 2026-11-18

Требование: извлечение, загрузка и обработка на своём сервере, без hosted
resolver/downloader API. Ранее добавленные обращения к стороннему сервису удалены.

## Причины задержек

- Instagram job 47: три попытки, отказ через 23 секунды.
- TikTok job 48: 24-минутный ролик; около 34 минут до отказа. Повторялись скачивания,

## Новый путь

Только TikTok `/player/api/v1/items?item_ids=...&aid=1988`, проверка ID и status_code.
Подписанный playback URL с неизменным query обслуживает собственный
`api16-normal-useast8.tiktokv.us`; редиректы/CDN проходят PublicHttp и SafeProxy.
H.264 приоритетнее HEVC. После получения валидного файла конвертация выполняется
один раз, вне цикла адресов. Oversize input сразу адаптируется под транспортный
лимит, с уменьшением разрешения/fps при низком битрейте. CLI ограничены deadline
45 секунд и не повторяют запросы внутри процесса. Повторы принадлежат очереди.
Ошибки лимитов и конвертации не перезапускают загрузчики; таймаут FFmpeg —
отдельный неретрайный processing_timeout.

## Предел работы над ссылкой — уточнение 2026-11-18

Пользователь выбрал максимум 1 минуту при целевой скорости 5–20 секунд.
`REQUEST_TIMEOUT_SECONDS=60` ограничивает работу над каждой ссылкой: извлечение,
скачивание, FFmpeg, fallback, автоматические повторы и отправку. Начальная очередь
и ожидание своей очереди на выдачу не расходуют срок. Подготовка параллельная,
файлы и ошибки выдаются по порядку. В SQLite сохраняются `active_elapsed`,
`active_since` и фаза обработки. Штатная остановка приостанавливает отсчёт;
при аварии восстановление ограничивает начисление последним heartbeat + 10 с.
Только явный новый запрос/кнопка пользователя начинает новый срок.

Перед каждой пачкой Telegram и повтором stale file_id проверяется оставшееся
время. Таймаут обработки отменяет дочерний процесс и запрещает поздний результат.
Таймаут во время upload сохраняется как uncertain без автоматического повтора:
уже принятый сервером Telegram запрос невозможно отозвать. Все подтверждённые
квитанции сохраняются; таймаут необязательной клавиатуры не отменяет факт доставки.

Реальная проверка в изолированном контейнере на VPS: временная БД, свежие ссылки,
штатные очередь/HTTP/FFmpeg, Telegram-отправка заменена spy и не выполнялась:

- Медленный 24-минутный TikTok: request_expired через 60,04 с; 0 вызовов отправки,
  work-каталог очищен, автоматического продолжения нет.
- Короткий TikTok: подготовлен за 5,31 с, очередь дошла до отправки в пределах срока.

Полный локальный прогон: 260 Python tests, FFmpeg/ffprobe, Deno и Chromium.
Добавлены проверки миграции, очереди, нового срока только для явного повторения,
отмены обработки, неопределённого upload и запрета следующей просроченной пачки.
Долгие ролики не пересылаются повторно для приёмки этой версии.


## Различие лички и Business на скриншоте

Один кешированный TikTok: Business job 54 — done за 5,43 с с квитанцией,
личка job 55 — uncertain после сетевого сбоя отправки примерно через 0,1 с.
Это не разные загрузчики. Найдена отдельная ошибка: uncertain подавлял новую
ссылку в другом сообщении. Теперь новое сообщение допускается, старое обновление
остаётся идемпотентным. Неопределённая отправка не повторяется автоматически.
Безопасный повтор разрешён только для ClientConnectorError до HTTP-запроса;
для остальных сетевых сбоев сохраняется uncertain. Диагностика содержит класс
причины, без текстов запросов/токенов.

Добавлены проверки одинакового кеша/режима для лички, группы и обеих сторон
Business, изоляции настроек, отзыва разрешений, параллельной подготовки,
порядка ошибок и файлов, готовых задач после перезапуска и очереди вне лимита.
Одиночная Live Photo длиной 6,4 с проверяется реальным FFmpeg без отсечения до 5 с.
Доступность motion у ранее проблемного поста остаётся неподтверждённой.

## Группа 111 — 2026-11-18

После назначения бота администратором обычные сообщения со ссылками доходят.
Два TikTok в одном сообщении доставлены в исходном порядке; повтор второй ссылки
не создаёт третью задачу. Результат использует те же файлы, что личный чат.
Отдельно приняты слайдшоу, исходный смешанный альбом фото/видео и аудиофайл.

В живом клиенте обнаружена проблема: клавиатура на участнике фотоальбома не видна.
Попытка editMessageReplyMarkup возвращает message is not modified для обоих
участников. Дополнительные кнопки перенесены в отдельный ответ на альбом.
Отказ/неопределённый результат этого ответа не повторяет уже принятый альбом;
восстановление по сохранённому checkpoint также пропускает повтор кнопок.
